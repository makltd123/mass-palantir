# Изменения

Формат: заметные изменения, новые сверху.

## Не выпущено

### Исправлено

- **v3 падала с `KeyError: 'id'` на «грязных» данных** — то есть на данных, под
  которые проект и задуман. Этап «низкий остаток» брал имена столбцов из
  хардкода (`id`, `inventory_id`), а в «грязных» таблицах те же поля называются
  `sku_code` и `item_ref`. Этапы 4-6 не выполнялись вовсе. Имена столбцов теперь
  выводятся из профиля данных (`resolve_roles`), и пайплайн проходит и на
  чистых, и на «грязных» данных.
- **FK-детекция давала ложные связи.** Условие «пересечение ≥ 50% своих
  значений» означало, что `purchase_requests.quantity` «ссылается» на
  `order_items.id`. Добавлены проверки: уникальность столбца-родителя, почти
  полное вложение значений дочернего столбца, доля использованных ключей
  родителя, совпадение типов, исключение столбцов-величин и ссылок внутрь своей
  же таблицы.
- **Без ключа API поиск дублей находил кандидатов, но подтверждал ноль** —
  recall падал до 0%. Добавлено эвристическое подтверждение (совпадение email и
  города либо высокое сходство названий): на «грязных» данных теперь precision и
  recall по 100% без обращения к LLM.
- **Короткие числовые ключи попадали в «мусор»** (`category_id`,
  `warehouse_id`) и выбрасывались из графа вместе с настоящим мусором
  (`flag_2`, `status_old_v1`).
- **Этап сверки проверял не то, что нужно.** Ключ ответов был зашит в код и
  описывал чистые данные: четыре «legacy-поля» на самом деле назывались `id` и
  `customer_id`, а списки дублей и мусорных столбцов были пустыми, поэтому
  проверки проходили сами собой. Ключ теперь читается из `answer_key.json`,
  который сохраняет `generate_dirty_data.py`; если файла нет, проверки
  пропускаются, а не имитируются. Исправлен и подсчёт итога: строка с precision
  и recall раньше всегда считалась провалом.
- **`int()` на идентификаторах клиентов** ронял этап дублей на нечисловых
  ключах.
- **Пустая таблица роняла профилирование** (`rows[0]` на пустом списке).
- **`orders.csv` перезаписывался без возможности откатиться** — теперь рядом
  создаётся `.bak`, а неразобранные даты попадают в отчёт, а не исчезают молча.
- **Разбор ответа модели.** Снятие ```-обёртки падало на ответе без перевода
  строки. Добавлены запрос `response_format={"type": "json_object"}`, поиск
  JSON внутри текста и проверка структуры ответа.
- **Путь импорта Mistral SDK** различается между версиями — поддержаны оба
  (`mistralai.Mistral` и `mistralai.client.Mistral`).
- **`check_low_stock` делала линейный поиск по заказам для каждой позиции** —
  заменено индексом по дате заказа.

### Добавлено

- Ключи командной строки у `ontology_builder_v3.py`: `--data-dir`, `--output`,
  `--stock-threshold`, `--model`, `--no-llm`, `--no-write`, `--save-profiles`.
  Таблицы ищутся по расширению в каталоге, поэтому можно подложить свои файлы.
- `--out-dir` у обоих генераторов: данные можно генерировать, не перезаписывая
  файлы репозитория.
- Эвристический граф сущностей на случай недоступной LLM: раньше без ключа
  граф был пустым.
- Фолбэки вместо падений: отсутствующая или пустая таблица пропускает
  соответствующий этап.
- Код возврата `1`, если провалена проверка этапа сверки.
- Тесты (`pytest`, 33 проверки) и линтер (`ruff`), GitHub Actions на Python
  3.11/3.12/3.13 со сквозным прогоном на «грязных» данных.
- `requirements-dev.txt`: `mistralai` отделён от `pandas`/`Faker`, которые
  нужны только генераторам.
- `examples/run_dirty_no_llm.md` — полный лог прогона без LLM.
- Раздел README о рисках: передача персональных данных в LLM, prompt injection
  из содержимого CSV, границы FK-эвристики.
