# Массовый палантир

[English](README.md) | **Русский**

Прототип, который сам строит онтологию компании из разрозненных CSV-таблиц. Он находит сущности (Клиент, Заказ, Товар и т.д.), связи между ними и одинаковые по смыслу поля в разных таблицах, даже если они называются по-разному. Идея похожа на Ontology в Palantir Foundry, только «для масс»: вместо команды внедрения — несколько CSV-файлов и LLM.

Главное свойство: имена столбцов не используются как источник истины. Ключи и связи выводятся из самих значений, поэтому `f_17`, `ref_9`, `sku_code` и `item_ref` распознаются как идентификаторы наравне с `id` и `customer_id`.

## Что делает v3

1. **Профилирование данных.** Для каждого столбца считает заполненность и долю уникальных значений. Находит последовательные целые числа (признак первичного ключа) и внешние ключи по пересечению значений между таблицами. Отмечает столбцы, похожие на мусор.
2. **Разрешение ролей столбцов.** Определяет, какой столбец в каждой таблице является первичным ключом, названием и внешним ключом. Прикладные этапы опираются на это, а не на зашитые имена полей.
3. **Классификация столбцов.** LLM делит столбцы на бизнес-поля, ключи и мусор, опираясь на профиль.
4. **Граф сущностей.** LLM описывает сущности, связи и соответствия полей между таблицами.
5. **Поиск дублей клиентов в два шага.** Сначала нормализация названий и нечёткое сравнение (`difflib`), затем подтверждение кандидатов — LLM или эвристикой.
6. **Нормализация дат** в `orders.csv`: `ДД.ММ.ГГГГ` → `ГГГГ-ММ-ДД`. Перед перезаписью создаётся `orders.csv.bak`.
7. **Правило «низкий остаток».** Для товаров с остатком ниже порога считает скорость расхода по заказам и число дней до исчерпания, предлагает объём закупки.
8. **Сверка с ключом ответов.** Если рядом с данными лежит `answer_key.json`, проверяет найденные legacy-поля, дубли (precision и recall) и мусорные столбцы.

Без ключа Mistral скрипт работает целиком на эвристиках: столбцы классифицируются по профилю, граф строится из найденных ключей и связей, дубли подтверждаются по совпадению email и города. На «грязных» данных такой прогон проходит все 8 проверок — см. [examples/run_dirty_no_llm.md](examples/run_dirty_no_llm.md).

## Данные

Данные синтетические, сгенерированы библиотекой Faker (`ru_RU`). Все названия компаний, имена, телефоны и email вымышленные. Это 10 таблиц машиностроительной компании: `customers`, `contacts`, `product_categories`, `inventory`, `warehouses`, `suppliers`, `supplier_contracts`, `orders`, `order_items`, `purchase_requests`.

- `generate_realistic_data.py` — чистые данные. Именно они сейчас лежат в репозитории.
- `generate_dirty_data.py` — те же таблицы с типичной «грязью» из реальных систем: переименованные legacy-ключи (`f_17`, `ref_9`, `sku_code`, `item_ref`), дубли клиентов, опечатки, разные форматы дат, мусорные столбцы. Печатает ключ ответов и сохраняет его в `answer_key.json`.

Оба генератора принимают `--out-dir`, поэтому данные можно сгенерировать в отдельный каталог и не перезаписывать файлы репозитория:

```bash
python generate_dirty_data.py --out-dir ./demo
```

## Версии

| Файл | Что это |
|---|---|
| `ontology_builder.py` | v1: первый прототип на трёх таблицах со старыми названиями полей (`client_ref`, `item_code`). Рассчитан на формат данных, которого в репозитории уже нет, и оставлен для истории (из линтера исключён). |
| `ontology_builder_v2.py` | v2: 10 таблиц, «грязные» данные, сверка с ключом ответов. Без ключа API не имеет фолбэков, поэтому проходит только часть проверок. |
| `ontology_builder_v3.py` | v3: актуальная версия. Профилирование, разрешение ролей столбцов, двухшаговый поиск дублей, эвристики на случай, если LLM недоступна. |

Результаты запусков лежат в `ontology_graph.json` (v1), `ontology_v2_graph.json` и `ontology_v3_graph.json`.

## Запуск

```bash
pip install -r requirements.txt          # только mistralai
pip install -r requirements-dev.txt      # + pandas, Faker, pytest, ruff

export MISTRAL_API_KEY="..."             # необязательно
export PYTHONUTF8=1                      # для символов ✓ и ✗ в консоли Windows

python generate_dirty_data.py --out-dir ./demo
python ontology_builder_v3.py --data-dir ./demo
```

В PowerShell переменные задаются как `$env:MISTRAL_API_KEY = "..."`.

### Ключи командной строки

| Ключ | Что делает |
|---|---|
| `--data-dir DIR` | каталог с CSV-файлами (по умолчанию — каталог скрипта) |
| `--output FILE` | куда сохранить результат (по умолчанию `ontology_v3_graph.json` в `--data-dir`) |
| `--stock-threshold N` | порог остатка для рекомендаций (по умолчанию 10) |
| `--model NAME` | модель Mistral (по умолчанию `mistral-small-latest`) |
| `--no-llm` | не обращаться к LLM, работать только на эвристиках |
| `--no-write` | не перезаписывать CSV-файлы (не нормализовать даты) |
| `--save-profiles` | положить профили столбцов в файл результата |

Код возврата: `0` — все проверки этапа сверки пройдены (или сверять нечего), `1` — хотя бы одна проверка провалена. Это удобно для CI.

Скрипт перезаписывает `orders.csv` при нормализации дат (рядом остаётся `.bak`) и файл результата. С `--no-write` CSV не меняются.

Таблицы ищутся по расширению `.csv` в `--data-dir`, поэтому можно подложить свои файлы. Прикладные этапы (дубли, остатки) включаются только если нужные таблицы есть: `customers` для дублей, `inventory` и `order_items` для остатков.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest
ruff check .
```

Тесты генерируют данные во временный каталог и не трогают файлы репозитория. То же самое прогоняется в CI на Python 3.11, 3.12 и 3.13.

## Ограничения и риски

- **Масштаб.** Рассчитан на небольшие таблицы: клиенты сравниваются попарно (O(n²)), FK-детекция перебирает все пары столбцов, а образцы строк из всех таблиц уходят в LLM одним промптом.
- **Эвристика FK не доказывает связь.** Совпадение значений — это признак, а не доказательство: на суррогатных целочисленных ключах диапазоны пересекаются случайно. Поэтому требуется почти полное вложение значений, уникальность столбца-родителя, совпадение типов, существенная доля использованных ключей родителя; столбцы-величины (`quantity`, `price`, `stock`, ...) без намёка в имени ссылками не считаются. Ложные срабатывания всё равно возможны — результат стоит просматривать глазами.
- **Данные уходят в LLM.** В промпты попадают образцы строк: названия компаний, email, телефоны. Для реальных данных это передача персональных данных внешнему сервису — используйте `--no-llm` или локальную модель.
- **Содержимое CSV попадает в промпт как текст.** Это открывает возможность prompt injection: строка в данных может содержать инструкции для модели. Этапы с LLM переживают мусорный ответ (переключаются на эвристику), но доверять графу на недоверенных данных не стоит.
- **Ответ модели разбирается как JSON.** Если модель отвечает не JSON-ом, этап переключается на эвристику.
- **Ключ ответов — только для синтетических данных.** На своих данных этап сверки нечего сверять: `answer_key.json` отсутствует, и проверки пропускаются.
