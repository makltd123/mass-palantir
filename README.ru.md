# Массовый палантир

[English](README.md) | **Русский**

Прототип, который сам строит онтологию компании из разрозненных CSV-таблиц. Он находит сущности (Клиент, Заказ, Товар и т.д.), связи между ними и одинаковые по смыслу поля в разных таблицах, даже если они называются по-разному. Идея похожа на Ontology в Palantir Foundry, только «для масс»: вместо команды внедрения — несколько CSV-файлов и LLM.

## Что делает v3

1. **Профилирование данных.** Для каждого столбца считает заполненность и долю уникальных значений. Находит последовательные целые числа (признак первичного ключа) и внешние ключи по пересечению значений между таблицами. Отмечает столбцы, похожие на мусор.
2. **Классификация столбцов.** LLM делит столбцы на бизнес-поля, ключи и мусор, опираясь на профиль.
3. **Граф сущностей.** LLM описывает сущности, связи и соответствия полей между таблицами.
4. **Поиск дублей клиентов в два шага.** Сначала нормализация названий и нечёткое сравнение (`difflib`), затем LLM подтверждает найденных кандидатов.
5. **Нормализация дат** в `orders.csv`: `ДД.ММ.ГГГГ` → `ГГГГ-ММ-ДД`.
6. **Правило «низкий остаток».** Для товаров с остатком меньше 10 считает скорость расхода по заказам и число дней до исчерпания, предлагает объём закупки.
7. **Сверка с ключом ответов.** Проверяет найденные legacy-поля, дубли (precision и recall) и мусорные столбцы.

Без ключа Mistral скрипт тоже работает, но только на эвристиках: столбцы классифицируются по профилю, а граф сущностей и подтверждение дублей пропускаются.

## Данные

Данные синтетические, сгенерированы библиотекой Faker (`ru_RU`). Все названия компаний, имена, телефоны и email вымышленные. Это 10 таблиц машиностроительной компании: `customers`, `contacts`, `product_categories`, `inventory`, `warehouses`, `suppliers`, `supplier_contracts`, `orders`, `order_items`, `purchase_requests`.

- `generate_realistic_data.py` — чистые данные. Именно они сейчас лежат в репозитории.
- `generate_dirty_data.py` — те же таблицы с типичной «грязью» из реальных систем: переименованные legacy-ключи (`f_17`, `ref_9`, `sku_code`, `item_ref`), дубли клиентов, опечатки, разные форматы дат, мусорные столбцы. Печатает ключ ответов.

Оба генератора пишут в одни и те же файлы, поэтому каждый запуск перезаписывает предыдущие данные.

## Версии

| Файл | Что это |
|---|---|
| `ontology_builder.py` | v1: первый прототип на трёх таблицах со старыми названиями полей (`client_ref`, `item_code`). Рассчитан на формат данных, которого в репозитории уже нет, и оставлен для истории. |
| `ontology_builder_v2.py` | v2: 10 таблиц, «грязные» данные, сверка с ключом ответов от `generate_dirty_data.py`. |
| `ontology_builder_v3.py` | v3: добавлены профилирование данных, двухшаговый поиск дублей и эвристики на случай, если LLM недоступна. Ключ ответов настроен под чистые данные. |

Результаты запусков лежат в `ontology_graph.json` (v1), `ontology_v2_graph.json` и `ontology_v3_graph.json`. Сохранённый результат v3 получен в запуске, где модель не ответила: граф сущностей в нём пустой, а столбцы классифицированы эвристикой.

## Запуск

```powershell
pip install -r requirements.txt
$env:MISTRAL_API_KEY = "..."   # необязательно: без ключа работают только эвристики
$env:PYTHONUTF8 = "1"          # чтобы символы ✓ и ✗ печатались в консоли Windows

python generate_realistic_data.py   # или generate_dirty_data.py
python ontology_builder_v3.py
```

`ontology_builder_v3.py` перезаписывает `orders.csv` (нормализует даты) и `ontology_v3_graph.json`.

## Ограничения

- Рассчитан на небольшие таблицы: клиенты сравниваются попарно, а в LLM уходят образцы строк из всех таблиц.
- Ответ модели разбирается как JSON. Если модель ответит в другом формате, этап переключается на эвристику.
